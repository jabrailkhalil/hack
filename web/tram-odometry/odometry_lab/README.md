# Odometry lab

Рабочая среда для проверки гипотез резервной одометрии: веб-интерфейс, Python API, CLI, воспроизводимые эксперименты и ROS 2 Humble-адаптер. Исходные данные читаются из соседней папки `dataset`. Экспериментальные модели из веток odometry_lab и зафиксированные ядра hack объединены общим причинным планировщиком.

## Веб-интерфейс в Docker

Из этой директории выполните `docker compose up -d --build` и откройте [localhost:8080](http://localhost:8080).
Карта OSM, фактическое и прогнозное положение трамвая, синхронные графики скорости/пути и ошибок,
сравнение моделей, отказы датчиков, обучение A/B/C и подбор параметров. Данные монтируются только
для чтения, результаты сохраняются. [Инструкция и методика веб-стенда](WEB.md).

Сводка уже выполненных проверок и ссылки на результаты: [VALIDATION.md](VALIDATION.md).

Первый набор алгоритмов — удержание скорости передней тележки, задней тележки и среднего двух датчиков. Это базовые оценки для сравнения, **не готовая модель компенсации проскальзывания**. Положение означает относительную продольную координату `s`, а не ENU-траекторию.

## Быстрый старт в Windows

Все команды ниже выполняются из `D:\hackathon\odometry_lab`. Активация окружения не требуется.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install --no-build-isolation --no-deps -e .
.\.venv\Scripts\python.exe -m pytest -q
```

```powershell
.\.venv\Scripts\tram-lab.exe inspect
.\.venv\Scripts\tram-lab.exe prepare --bags 30618_0e41eac3 30639_0be558e2
.\.venv\Scripts\tram-lab.exe split --output .cache/split.json
.\.venv\Scripts\tram-lab.exe run --config configs/mean.yaml --bags 30618_0e41eac3 30639_0be558e2 --output runs/mean
.\.venv\Scripts\tram-lab.exe run --config configs/front.yaml --bags 30618_0e41eac3 30639_0be558e2 --output runs/front
.\.venv\Scripts\tram-lab.exe compare runs/mean runs/front --output runs/comparison
```

Откройте `runs/mean/report.html` или `runs/comparison/report.html`. Запуск с существующей выходной директорией отклоняется: выберите новое имя, предыдущие результаты не перезаписываются. Без `--bags` запускаются все уникальные записи; это сознательный выбор объёма эксперимента, не короткий smoke-test.

`inspect` заново читает метаданные и хеширует базы. Для данного архива ожидаются 122 записи, 97 уникальных баз, 25 дубликатов и 8 788 325 сообщений. Декодируются только выбранные bag; кеш хранится в `.cache`, исходники не изменяются.

## Конфигурации и выборки

Пути внутри YAML разрешаются относительно самого YAML. Пути аргументов CLI — относительно текущей директории. Типичная конфигурация:

```yaml
dataset: ../../dataset
cache: ../.cache
bags: [30618_0e41eac3]
estimator:
  name: mean                  # front | rear | mean
  wheel_scale: 0.2777777777777778
  stale_after_s: 0.5
period_ms: 50
tolerance_ms: 50
seed: 42
plots: true
quality: {}                   # никакой неявной очистки эталона
faults: []
```

Масштаб `1/3.6` задан явно: он соответствует эмпирической проверке предоставленного архива и должен быть подтверждён для других источников. Сырые значения остаются в кеше. Оцениватель получает их без предварительного масштабирования и сам применяет свой коэффициент ровно один раз.

Для выборки вместо `bags` укажите `split_file: ../.cache/split.json` и `subset: train`, `validation` или `test`. Одновременно выбирать `bags` и `split_file` нельзя. Разбиение делается по целым уникальным поездкам, по времени внутри каждого префикса: 70%/15%/остаток, с округлением первых двух долей вниз. Получаются 67/13/17 поездок. Это разбиение не гарантирует независимость маршрутов.

```powershell
.\.venv\Scripts\tram-lab.exe split --strategy cross_vehicle --train-vehicle 30618 --output .cache/cross_30618_to_30639.json
.\.venv\Scripts\tram-lab.exe split --strategy cross_vehicle --train-vehicle 30639 --output .cache/cross_30639_to_30618.json
.\.venv\Scripts\tram-lab.exe run --config configs/cross_30618_to_30639.yaml --output runs/cross_vehicle
```

При переносе 85% поездок исходного трамвая используются как train, остальные как validation, все уникальные поездки другого — как test. Стенд не обучает модель автоматически; это только фиксированные списки для будущих экспериментов. В split сохраняются SHA-256, несовпадение данных обнаруживается до запуска.

## Отказы и эталон

`configs/faults.yaml` показывает все пять искажений: `drop`, `delay`, `spike`, `freeze`, `scale`. Интервалы задаются в секундах от начала bag, полуоткрыто: `[start_s, end_s)`. По умолчанию затрагиваются обе тележки; `topics` выбирает конкретные разрешённые входы. Амплитуда выброса задаётся в сырых входных единицах. `freeze` удерживает последнее значение перед началом интервала; если его нет — первое внутри. При вероятности меньше единицы отбор выполняется отдельно для каждого события.

Задержка меняет только время доставки. Метки измерения сохраняются; события снова упорядочиваются по доставке и исходному sequence. Задержанные за конец bag сообщения не продлевают оцениваемый прогон. GNSS ни один из преобразователей не изменяет.

```powershell
.\.venv\Scripts\tram-lab.exe run --config configs/faults.yaml --bags 30618_0e41eac3 --output runs/faults
```

Эталон скорости — `hypot(vx, vy)` из master, если этот поток содержит сообщения, иначе из rover. Используется ближайший `header.stamp` с допуском 50 мс. Ближайшая точка может быть позже оценки: это только офлайн-сопоставление эталона, не вход алгоритма. Нули master не заменяются на rover автоматически.

По желанию можно добавить явно описанную дополнительную маску:

```yaml
quality:
  max_receiver_disagreement_mps: 0.5
  exclude_intervals_s: [[100, 110]]
```

При таком пороге отсутствие второго приёмника также исключает точку из дополнительной маски. Сырые метрики всегда сохраняются рядом с отфильтрованными, вместе с покрытием и числом исключённых отсчётов. Порог приведён как пример, а не как установленный критерий качества GNSS.

## Сохранённые результаты

Каждый запуск содержит:

- `config.yaml` и `config.json` — разрешённые пути и параметры эксперимента;
- `provenance.json` — хеш кода ядра, хеши bag, версии, Python, платформа и seed;
- `metrics.json` / `metrics.csv` — результаты по bag и объединённые ошибки скорости;
- `resources.json` — время обработки, CPU и измеренный с шагом 20 мс пик RSS процесса;
- `bags/<id>/predictions.csv` — все такты, включая `unavailable`, обе оценки возраста, скорость, путь, эталон, маски и ошибка;
- `bags/<id>/signals.png` — скорости, интегральный путь, невязки, команда, возраст;
- `report.html` — сводный отчёт.

`prediction_coverage` — доля тактов с оценкой. `coverage` — доля всех тактов с конечной оценкой и сопоставленным конечным GNSS-эталоном. Объединённый RMSE взвешивается числом отсчётов; отдельно показан средний RMSE по bag. Bag без GNSS имеет доступные показатели публикации, но точность `null`/N/A.

**Метрики пути считаются по непрерывным сопоставленным участкам**, с собственной начальной привязкой каждого участка. Эталонный путь — интеграл горизонтальной GNSS-скорости на сетке сопоставленных тактов. Пропуски не мостятся. `covered_end_error_sum_m` суммирует ошибки концов этих участков, а `full_interval_end_error_m` доступна только при полном покрытии интервала доступных оценок одним участком. Это не 3D-ошибка позиции и не официальный скрипт судьи. При длине эталонного пути менее 1 м процентный дрейф не считается.

Время быстрого офлайн-проигрывания не равно задержке ROS-ноды. Для неё предназначен отдельный тест ниже.

## ROS 2 Humble в Docker

Docker Desktop должен работать в режиме Linux containers. Первый build скачивает Ubuntu/ROS-зависимости и Python-пакеты; последующий запуск и `colcon build` выполняются без сети.

```powershell
.\.venv\Scripts\tram-lab.exe ros-smoke --build --output artifacts/ros-smoke
```

Команда собирает образ `tram-odometry-lab:humble`, запускает контейнер с `--network none --cpus 2 --memory 512m`, монтирует `dataset` только для чтения и сохраняет результаты на хосте. Внутри `colcon` собирает пакет `tram_vehicle_msgs` из смонтированного датасета и адаптер. Python-ядро заранее установлено из локального исходного кода при сборке образа.

В приложенном `package.xml` отсутствует обязательный `maintainer`. Подготовка workspace добавляет его только в копию внутри контейнера и записывает изменение в `workspace_preparation.json`. SHA-256 обоих `.msg` сверяются с источником; исходный пакет не меняется. Сборочные логи сохраняются в `runner.log`, включая ошибки до запуска ноды.

Smoke-test проверяет типы и поля выходов, 20 Гц по шкале `/clock`, остановку публикации при паузе, сброс пути при откате часов, две публикации реального bag и точное совпадение общего ядра при офлайн-воспроизведении записанного порядка ROS-callback. Проверка включает задержки от приёма входа callback до публикации; транспорт до callback в это измерение не входит. Результат — `smoke.json`, логи и JSONL-трассы. При неудаче команда возвращает ненулевой код, подробности остаются в артефактах.

В синтетической части дополнительно подаются NaN в обе колёсные скорости: нода должна сохранить конечную оценку и увеличить счётчик отказов. В строгом JSON трассы нечисловые входные значения представлены строками `nan`/`inf`/`-inf`, чтобы сохранить их поведение при повторном чтении. Wall-clock задержка синтетической части включает намеренную паузу часов; для оценки обычной задержки отдельно приведены результаты реального bag. Humble Player может при старте дополнительно откатывать clock на несколько десятков миллисекунд; эти события сохраняются в отчёте, поэтому число эпизодов может превышать число запусков bag.

Повторный тест без пересборки:

```powershell
.\.venv\Scripts\tram-lab.exe ros-smoke --output artifacts/ros-smoke-repeat
```

После изменения Python-ядра или адаптера образ необходимо пересобрать с `--build`. Для ручного запуска на подготовленном bag:

```powershell
docker run --rm --network none --cpus 2 --memory 512m --mount "type=bind,source=D:\hackathon\dataset,target=/dataset,readonly" --mount "type=bind,source=D:\hackathon\odometry_lab\artifacts,target=/artifacts" tram-odometry-lab:humble bash
```

Для интерактивной оболочки добавьте `-it`. В контейнере окружение Humble и собранного workspace уже подключено. Запускайте проигрыватель и ноду в этом же контейнере; например через отдельные фоновые процессы shell. Нода запускается так:

```bash
ros2 run tram_lab_ros estimator --ros-args -p use_sim_time:=true -p estimator:=mean
# В том же контейнере: ros2 bag play <prepared-bag-directory> --clock 100
```

Входы: `/vehicle/front_bogie_velocity`, `/vehicle/rear_bogie_velocity`, `/vehicle/driver_position_cmd`. GNSS-подписок у ноды нет. Выходы: `/result/velocity`, `/result/position`, `/diagnostics`.

Поза публикуется как `(s, 0, 0)` в `track_relative`, скорость — в `base_link`. Ориентация единичная. Ковариации — большие консервативные заглушки `1e6` по диагоналям, а не калиброванные вероятностные оценки. При недостатке данных до первой оценки публикация результата отсутствует; затем скорость удерживается с диагностикой устаревания. Это поведение базового алгоритма, а не стратегия безопасности для реального трамвая.

## Python API и новая гипотеза

```python
from tram_lab.data import build_manifest, read_bag
from tram_lab.estimators import WheelEstimator
from tram_lab.replay import replay
from tram_lab.metrics import compute_metrics

manifest = build_manifest("../dataset", ".cache")
record = next(r for r in manifest["bags"] if r["id"] == "30618_0e41eac3")
events = list(read_bag(record, ".cache", "../dataset/tram_vehicle_msgs/msg"))
estimates = list(replay(events, WheelEstimator({"name": "mean"}),
                        record["start_ns"], record["end_ns"]))
metrics = compute_metrics(estimates, events)
```

Новый оцениватель реализует `reset(config)`, `update(Event)` и `predict(time_ns) -> Estimate`. В конфигурации укажите `estimator.factory: package.module:ClassName`; фабрика вызывается без аргументов, затем выполняется `reset`. Конфигурации с фабрикой предназначены для доверенного локального кода. Готовый пример причинного фильтра находится в `src/tram_lab/example.py`, запуск — через `configs/example.yaml`. Он демонстрирует расширение API, не обещает улучшения точности.

В `tram_lab.signals` доступны преобразование единиц, причинная производная, интегрирование, выделение интервалов и сопоставление эталона. Последняя функция двунаправленная и предназначена только для оценки. Архитектура и договорённости описаны в [ARCHITECTURE.md](ARCHITECTURE.md).

## Воспроизводимая приёмка датасета

```powershell
.\.venv\Scripts\python.exe scripts/validate_dataset.py --output artifacts/validation
```

Проверяет полный manifest и разделение дубликатов, дважды обрабатывает длинные записи `30618_0e41eac3` и `30639_0be558e2`, а также запись без GNSS `30618_0a83c933`. Численные метрики и CSV предсказаний должны совпасть; время и RSS закономерно могут различаться. Сохраняет `verification.json` и отчёты. Это проверка реализации стенда, не отложенная оценка качества будущей модели.

## Ограничения v1

- Один SQLite-файл на bag; многотомные bag и другие форматы хранения отклоняются.
- Декодированные данные одной поездки и отчёт загружаются в память; обработка разных поездок последовательная. ROS-нода не загружает архив или историю поездки.
- Кеш предназначен для локального доверенного использования. Ручное изменение NPZ не поддерживается; для повторной проверки декодирования используйте новый `--cache`.
- Не восстанавливаются неизвестная геометрия пути, направление на развилках или высота. Начальная GNSS-выставка и обучение не реализованы.
- Нет EKF, тяговой динамики и компенсации общего скольжения; контроллер доступен расширениям, но три базовые оценки его не используют.
- Отдельные такты реального ROS-воспроизведения могут зависеть от DDS-доставки. Проверяется точное совпадение ядра на **одной и той же записанной трассе событий**, а не побитовое совпадение разных сетевых запусков.
