# Выполненная проверка среды

Проверены Python API/CLI в Windows с Python 3.12.10 и контейнер ROS 2 Humble с Python 3.10.12. `hack` не просматривался; исходный датасет использовался только для чтения.

## Автоматические проверки

- **20 тестов прошли в обоих окружениях.** Проверены наносекундная точность, единицы, три базы, причинность, отсутствие GNSS в оценивателе, пропуски/отказы, временные скачки, схемы сообщений, кеш, выборки и повторяемость. Linux JUnit: `artifacts/pytest-linux.xml`.
- Manifest из исходного архива: **122 bag, 97 уникальных баз, 25 дубликатов, 8 788 325 сообщений**. Хеши групп не пересекаются между train/validation/test; размеры выборок 67/13/17.
- Два полных прогона каждой из трёх записей дали одинаковые численные метрики и побайтово одинаковые CSV предсказаний. Подтверждение и хеши: `artifacts/validation/verification.json`.

## Длинные офлайн-прогоны

База `mean`, масштаб `1/3.6`, период 50 мс, сырой GNSS без дополнительной маски. Это приёмка стенда на доступных данных, не отложенная оценка будущей модели.

Отчёт: `artifacts/validation/mean/report.html`. Покрытие предсказаниями по трём bag — около 99,996%; пропуски в начале относятся к ожиданию первых необходимых измерений. Покрытие эталоном имеет другой знаменатель и не характеризует сбои публикации.

Также выполнены запуск с пятью типами искажений и запуск подключаемого причинного фильтра. Сравнение находится в `artifacts/comparison/report.html`. На показанном bag пример сглаживания ухудшает RMSE относительно mean — он оставлен как демонстрация расширения API, не как рекомендованная модель.

## Живая ROS-проверка

Успешный результат: `artifacts/ros-smoke-verified/smoke.json`.

- Сборка двух ROS-пакетов через `colcon` и весь тест выполнены с выключенной сетью, лимитом **2 CPU / 512 MiB**.
- Проверены точные типы выходных сообщений, согласованные скорость/позиция/метки, конечные значения, единичная ориентация, системы `track_relative` и `base_link`.
- Синтетическая проверка подтвердила **20 Гц**, отсутствие публикации при паузе clock, сброс пути после отката времени и отбрасывание NaN обоих колёсных датчиков без падения ноды.
- Короткий реальный bag `30618_0d865417` воспроизведён дважды: **233 пары выходов на каждый запуск**. Результат ядра полностью совпал с офлайн-воспроизведением записанного порядка ROS-callback.
- На реальном bag: от приёма callback до публикации **p95 17,96 мс, p99 26,48 мс, максимум 117,07 мс**. Это одна проверка на короткой записи при playback rate 2; не гарантия предельной задержки во всех условиях. Время доставки до callback не измерялось.
- RSS дерева процессов адаптера в синтетической проверке — около **83,7 MiB**, отдельный снимок, не пиковая память всего контейнера.

В синтетическом тесте максимальная wall-clock задержка около 459 мс включает намеренную паузу часов с ожидающим входом. Она сохранена в отчёте и не смешивается с показателями обычного проигрывания. Humble Player дополнительно дважды откатил clock примерно на 34–36 мс при стартах; адаптер зарегистрировал эти события отдельно от полного перематывания bag. Поэтому в реальном тесте четыре временных эпизода при двух запусках.

## Совместимость исходного пакета сообщений

В исходном `package.xml` отсутствует обязательный `maintainer`. Подготовка контейнера исправляет только рабочую копию, иначе `colcon` отклоняет пакет. Хеш исходного XML остался `56e728afaa2cd2f6a38ee42a720221cf77c8d7053f8235d7f6423ff8fba8212b`; определения обоих `.msg` также не изменены. Подробности — `workspace_preparation.json` рядом с ROS-отчётом.

Повторение проверки описано в README. Папки предыдущих неудачных ROS-проверок сохранены как диагностические артефакты; актуальный успешный результат указан выше.
