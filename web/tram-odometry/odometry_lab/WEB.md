# Веб-лаборатория одометрии

## Запуск

Из `odometry_lab`, с работающим Docker Desktop в режиме Linux containers:

```powershell
docker compose up -d --build
```

Открыть [localhost:8080](http://localhost:8080). Остановка: `docker compose stop`.
Повторный запуск: `docker compose up -d`. Обновление кода требует `--build`.
Первая сборка скачивает зависимости. После сборки расчёты и интерфейс работают
без сети; только подложка OSM загружается из интернета. Шрифты находятся в образе.

Ожидается `../dataset/data.zip` и `../dataset/tram_vehicle_msgs/msg`. Датасет
монтируется read-only. `runs/` и `models/` сохраняются на хосте; кеш и SQLite-очередь
находятся в именованных Docker volumes. `docker compose down` сохраняет их;
`docker compose down -v` удаляет кеш и историю очереди. Сервис доступен только на
loopback-интерфейсе компьютера. Это локальный стенд без многопользовательской авторизации.

## Рабочий процесс

1. **Новый эксперимент** → поездки или выборка → модели → запуск. В параметрах
   модели можно задать JSON-переопределения и выбрать сохранённую версию весов.
2. **Эксперименты** показывает очередь, журнал, отмену и повтор. Отметьте несколько
   сохранённых запусков, чтобы сравнить их на общих поездках.
3. Курсор графика и ползунок управляют одной шкалой времени. Поддерживаются пауза,
   ускоренное воспроизведение, масштабирование графиков, скрытие моделей и дополнительные
   числовые диагностические сигналы.
4. **Обучение** создаёт новые веса A/B/C. Можно ограничить train и validation
   поездками внутри соответствующего разбиения для короткой проверки.
5. **Подбор** выбирает параметры по объединённому RMSE скорости validation.
   Укажите диапазоны, например `{"core.max_age_s":{"min":0.15,"max":0.4}}`,
   или значения `{"physics":{"values":[true,false]}}`. Первый кандидат — исходная
   конфигурация, остальные — воспроизводимый случайный поиск с указанным seed.
6. Обученные версии доступны в разделе **Модели → Сохранённые версии** и в выборе весов. Test запускается отдельно
   через обычный эксперимент; подбор и обучение его не используют.

Раздел **Данные** содержит поиск, фильтры GNSS/трамвая и разбиения выборок;
выбранные поездки можно перенести в новый эксперимент. В боковом меню переключаются
светлая и тёмная темы. На странице анализа доступны вкладки скорости, пути,
диагностики и всех четырёх графиков. Происхождение оформления: [frontend/DESIGN.md](frontend/DESIGN.md).

Пустой список ограничений train/validation означает всю соответствующую выборку.
Поездки вне неё и дубликаты отклоняются. Бюджет по умолчанию — 24 кандидата,
минимальное покрытие — 95% от исходной конфигурации. Отказы и маска качества задаются
явно; при обучении отказы применяются к последующей validation-проверке, не к train-меткам.
Порог проверяется для совместного покрытия эталоном и доступности прогноза.
При смене разбиения проверяется и происхождение сохранённых весов/подобранных параметров:
ранее использованные данные не могут незаметно стать новым validation/test.
Число над графиком относится к первому видимому запуску, вся таблица — к полной поездке.

## Значение карты и графиков

Модель оценивает скорость и продольный путь; точка прогноза на карте — **офлайн-проекция**
этого пути на упорядоченный GNSS-маршрут. GNSS не передаётся оценивателю. D — модуль
геометрии, поэтому не выдаётся за дополнительную модель скорости.

Маршрут строится из master/fix, либо rover/fix при полном отсутствии master.
Невалидные координаты, GNSS status < 0, неположительное приращение времени,
разрыв больше 1 с или географический скачок больше `max(50 м, 60 м/с × dt)`
разделяют отображаемый маршрут на участки. Эти правила не меняют метрики.
Прогноз привязывается один раз в начале совместно доступного участка; после
географического разрыва начинается новая локальная привязка. За пределами маршрута
маркер отсутствует. Реальный маркер показывает ближайший исходный fix с допуском
250 мс. Сплайн изменяет только линию маршрута, не GNSS-точки, оценки или ошибки.

Эталон скорости и ошибки полностью повторяют `tram_lab.metrics`. Путь на графике
сравнения — интеграл GNSS-скорости по непрерывным сопоставленным участкам, прогноз
имеет общую локальную начальную привязку на каждом участке. Разрывы не соединяются;
ошибка всегда «прогноз минус эталон». Это не 3D-ошибка положения. Без GNSS показывается
доступный накопленный путь модели, ошибки и эталон остаются недоступными.

Прореживание применяется только к отображению: сохраняются экстремумы каждого
показателя, границы пропусков и участков. Метрики, CSV и обучение используют все
отсчёты. В браузер абсолютные наносекунды передаются строками, время графиков —
секундами от начала bag. Старые CSV читаются без повторного запуска модели;
перед загрузкой географии проверяется хеш исходной поездки.

## Модели и происхождение

Каталог содержит front/rear/mean, A/B/C/H1/H2 и hack v5–v8. Экспортированные
A/B/C/H1/H2 из `hack/experiments/tram-*` проверены по исходникам и весам и обозначены
алиасами. H1 по умолчанию — вариант 10: перенос возраста включён, физика выключена.
H2 использует историю 0,5 с и фиксированную сетку 50 мс.

`src/tram_lab/model_sources.json` содержит исходные commit SHA и SHA-256 файлов.
v5–v8 являются фиксированными профилями экспортированного ядра, а не историческими
бинарными сборками. Адаптер сохраняет проверку входов Timeline и Observer.step,
но публикацией управляет планировщик odometry_lab по received_ns. Поэтому старые
метрики native Timeline нельзя напрямую выдавать за результаты нового replay.

Обучение A/B использует существующий robust ridge по согласованным свежим TRAIN-колёсам,
C также обучает ограниченную остаточную поправку. GNSS не используется как обучающая
метка. Сохранённые исходные веса обучались на синтетике; качество новых моделей
на реальных поездках определяется отдельными результатами, без обещания улучшения.

CLI-контракт `estimator.factory: package.module:ClassName` сохранён. Например:

```yaml
estimator:
  factory: tram_lab.hack_adapter:HackEstimator
  profile: hack_v8
  wheel_scale: 0.2777777777777778
```

Для собственного доверенного плагина установите его в образ и укажите
`TRAM_MODEL_REGISTRY` в окружении обоих сервисов, например `/runs/custom_models.json`:

```json
[{"id":"custom","label":"Моя гипотеза","factory":"my_package:Estimator","defaults":{"alpha":0.2}}]
```

Файл регистрируется локально, браузер не принимает произвольный Python-код или новые
factory-пути. URL подложки можно изменить через `TRAM_TILE_URL` окружения web.
Подложка OSM используется с атрибуцией и стандартным браузерным кешированием,
без массовой загрузки тайлов.

## API, хранение и проверки

OpenAPI: [localhost:8080/docs](http://localhost:8080/docs). Все методы используют
префикс `/api/v1`: `models`, `dataset`, `splits`, `jobs`, `runs`, `series`, `geometry`,
`artifacts`, `download`. POST `/jobs` принимает `{kind, request}`, где kind —
`experiment`, `train` или `tune`. GET `/jobs/{id}` возвращает журнал и состояние,
POST `/jobs/{id}/cancel` отменяет задание. Один worker исполняет задания последовательно
в отдельных процессах; отмена не блокирует веб-сервис. После перезапуска исполнявшееся
задание становится `interrupted`, ожидающие продолжают очередь.

Каждый запуск создаёт новый каталог `runs/web_<job>/<model-or-trial>/`. Конфигурация,
метрики, происхождение, диагностика и ресурсы сохраняются рядом с CSV. Версии весов
хранятся в `models/<id>/artifact.json` вместе с разбиением, хешами, seed, родительским
артефактом и validation-результатами. Исходные артефакты не перезаписываются.

```powershell
docker compose exec web python -m pytest -q
cd frontend
npm ci
npm test
npm run build
```

Реальная сквозная проверка создаёт новые эксперименты, обучение, три кандидата
подбора и отменённое задание; это smoke-проверка реализации, не итоговая оценка моделей:

```powershell
.\.venv\Scripts\python.exe scripts/validate_web.py --output artifacts/web-validation-new
```

Для разработки без Docker: установить `requirements.txt`, `requirements-web.txt` и пакет
`pip install -e .`, собрать frontend и запустить из odometry_lab в двух терминалах
`python -m uvicorn tram_lab.web.app:app --port 8080` и `python -m tram_lab.web.worker`.
