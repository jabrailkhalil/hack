# Точность и быстродействие v8

## Набор и методика

Сохранённая проверка содержит 19 validation-записей; в 15 доступен GNSS-эталон. Сопоставлены 30 пар «запись / приёмник» (master и rover), 698891 точка. Два приёмника одной поездки не считаются независимыми поездками. Четыре записи без GNSS не получают фиктивную нулевую ошибку.

В модель поступают только контроллер и две колёсные скорости. Эталон скорости — горизонтальная норма GNSS `sqrt(vx²+vy²)`, обработанная офлайн с сопоставлением по времени и проверкой доступности. Для всех сравниваемых оценивателей используются общие причинные входы и временная сетка 20 Гц.

`RMSE=sqrt(mean((v_est−v_ref)²))`. Group-macro — среднее RMSE по парам внутри группы, затем среднее по группам; pooled — RMSE по всем сопоставленным точкам. Разные способы агрегации приводятся отдельно.

## Сохранённые результаты

| Метрика | v8 | Среднее двух тележек |
|---|---:|---:|
| RMSE скорости по группам, м/с | 0.114550 | 0.175989 |
| RMSE скорости по всем точкам, м/с | 0.216407 | 0.347124 |
| RMSE в исходных окнах отказов, м/с | 0.538287 | 3.370559 |
| RMSE относительного пути по непрерывным участкам, м | 4.595481 | 14.576177 |

В исходных сценариях моделировались смещение переднего датчика, пропадание обеих колёсных скоростей на 5/10 с и общие нули на 3 с. Контроллер при пропадании колёс оставался доступен. Дополнительно проверены резкие общие скачки и плавный общий дрейф; всего 152 сценария. Для плавного дрейфа v8: RMSE 3.071476 м/с, среднее восстановление 4.4075 с.

Положение сравнивается со скалярным интегралом скорости GNSS на непрерывных участках с общей начальной точкой каждого участка. Сброс reference-origin делает эту метрику локальной: она не измеряет накопленный дрейф всего пути или XYZ-ошибку. Полная пространственная оценка требует внешней карты и начальной привязки.

Это повторно использованный validation-набор. Независимый итоговый тест текущего v8 по этим материалам не заявляется.

Исходные данные отчёта: [decision.json](../reports/adjudication/decision.json), [ошибка по каждой записи и приёмнику](../reports/adjudication/clean_per_bag.csv), [ошибки по типам отказов](../reports/adjudication/fault_by_type.csv), [полный протокол сравнения](../reports/adjudication/REPORT.md).

## Быстродействие

Профиль v8 задаёт 20 Гц и нулевую намеренную задержку выравнивания. Это настройки алгоритма, а не измеренная гарантия реального времени. Свежий полный замер текущей ROS-упаковки в доступных материалах отсутствует.

Для контекста сохранён исторический ROS-прогон **v4**, commit `0d2adcd82c714e0879f2786aa3937cf0189bce6b`, на development-записи продолжительностью 1460.462 с:

| Метрика исторического v4 | Измерено |
|---|---:|
| Частота выходов по реальному времени | 20.001 Гц |
| Пиковый RSS ноды и launcher | 80.70 MiB |
| CPU p95 / max | 0.090 / 0.130 ядра |
| Publisher → оба выхода после 10 с, p95 / max | 60.62 / 117.69 мс |

Эти значения относятся к v4 и не переносятся на v8. Полный исторический отчёт: [RESULTS.md](RESULTS.md), исходные измерения: [runtime_full.json](../reports/final/runtime_full.json).

Для нового измерения установленного v8 подготовлен `tools/benchmark_selected.py`. Команды, выходные файлы и критерии приведены в [инструкции жюри](JUDGE_GUIDE.md#5-задержка-частота-и-ресурсы). Результат нового запуска следует сохранять отдельно от исторических файлов.
