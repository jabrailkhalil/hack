# Поля 1 и 6 для формы сдачи

Готовый текст для копирования в форму по задаче «Резервная одометрия по модели».

## 1. Ссылка на пакет(ы) ROS 2 Humble

https://github.com/jabrailkhalil/hack/tree/main/src

В составе два ROS 2 Humble пакета: `reserve_odometry` и `tram_vehicle_msgs`.

Основной executable: `guarded_odometry_node`.  
Основная конфигурация: `champion_v8.yaml`.  
Штатный запуск:

```bash
ros2 launch reserve_odometry odometry.launch.py
```

Нода подписывается на входные топики:

- `/vehicle/driver_position_cmd` — положение контроллера;
- `/vehicle/front_bogie_velocity` — скорость передней тележки;
- `/vehicle/rear_bogie_velocity` — скорость задней тележки.

Публикуемые выходы:

- `/result/velocity` — оценка продольной скорости, м/с;
- `/result/position` — относительная одометрия;
- `/result/diagnostics` — диагностическая информация.

Сборка выполняется через `colcon`; штатные скрипты сборки и запуска находятся в каталоге `submission/`.

## 6. Описание ограничений решения и плана развития после хакатона

Текущая версия решает задачу резервной **продольной** одометрии и имеет следующие ограничения.

1. Положение публикуется как относительная along-track координата `(s, 0, 0)`. Полноценная GNSS/ENU XYZ-траектория не восстанавливается, поскольку в предоставленных данных не подтверждены карта пути, origin и однозначный маршрут прохождения стрелок.

2. Масштаб входных wheel-speed `1/3.6` является эмпирическим предположением, полученным по предоставленным данным, и должен быть подтверждён организаторами.

3. Параметры физической модели являются эффективными идентифицированными коэффициентами. Масса, радиус колеса, момент, сопротивления и другие величины не заявляются как независимо измеренные паспортные характеристики конкретного вагона.

4. Правдоподобная синхронная ошибка обоих wheel-каналов может быть неотличима от ошибки физической модели без независимого внешнего источника. Наиболее сложный известный сценарий — плавный common-mode drift обоих датчиков. На используемом validation-наборе для этого сценария event RMSE составляет 3.07148 м/с, среднее время восстановления — 4.41 с.

5. В режиме `input_stamp` при полном исчезновении всех входов модельное время перестаёт продвигаться. Для проверки полного dropout предусмотрен режим `ros_clock`.

6. Решение не является safety-certified системой и не предназначено для непосредственного использования в контуре управления движением без дополнительной промышленной верификации.

### План развития

- после уточнения контракта организаторов зафиксировать единую метрическую систему, карту маршрута и origin;
- реализовать разрешённую bounded GNSS-инициализацию только в начальном окне;
- перейти от `(s, 0, 0)` к привязке `xyz = r(s)` для известного маршрута и оценивать along-track/cross-track ошибку;
- провести cross-vehicle проверку переносимости модели на других вагонах;
- собрать независимый тестовый набор с размеченными сценариями проскальзывания и отказов;
- улучшить обнаружение медленного common-mode drift двух wheel-сенсоров;
- откалибровать covariance/uncertainty оценки скорости и положения;
- выполнить длительные ROS 2 проверки latency, CPU и RSS на целевом оборудовании;
- для промышленной версии добавить watchdog, обработку packet loss/clock faults, политику безопасной деградации и независимую верификацию требований.
