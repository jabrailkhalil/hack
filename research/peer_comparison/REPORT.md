# Сравнение с godknows1337/tram-odometry

## Версии и итог

Проверены `jabrailkhalil/hack` @ **e3b0c9c039d2953fbfcda51231263d38ef9f1024** (canonical champion_v8) и `godknows1337/tram-odometry` @ **0148c0563a781da18b1e25b57bd6e6ba15f45742**. Ни main, ни рабочие алгоритмы обоих репозиториев этой работой не изменялись.

**На проверенных записях наш v8 сильнее как алгоритм резервной одометрии. У товарища сейчас аккуратный исследовательский стенд с базовыми оценками, а не реализованная физическая модель тяги/торможения.** Его WheelEstimator принимает controller, но не использует его для расчёта скорости. Реализованы front/rear/mean; отдельный пример — сглаживание mean с tau=0.15 с. Это прямо обозначено автором как baseline и example, не final-модель.

## Методика

План сравнения сохранён до численных прогонов в этой ветке. Все 19 существующих validation-bag, 15 с GNSS, 9 reference-групп, 30 bag/receiver-пар. Оба GNSS-приёмника сохранены, nearest matching 50 мс. Четыре bag без эталона не засчитываются нулевой ошибкой. Параметры не подбирались, физика не переобучалась, final-test measurement DB не открывались.

Первичный эксперимент изолирует оцениватели: одна причинная сетка source time 20 Гц, одинаковые новые raw samples и held-значения. Peer получает только vehicle-входы, не выходы модели. Его точные types.py, estimators.py, example.py сверены по Git blob SHA и реально исполнены. Исходный масштаб 1/3.6 одинаковый. Stale-оценки peer остаются в метриках, потому что его код продолжает их численно публиковать. Это **не end-to-end сравнение двух штатных ROS-адаптеров**.

Наш runtime/config/evaluator взяты из проверенного snapshot, отличающегося от main лишь export-workflow и планом H13. Все исполняемые файлы сверены по хешам. Ожидаемая и полученная наша group-macro RMSE совпали точно: **0.1145498613174081**, n=**698891**. Численная маска одинакова для пяти оценивателей. Оценки peer до нашей инициализации отдельно подсчитаны; им не приписывается отсутствие публикации.

Group-macro — среднее RMSE внутри каждой группы записей/приёмников, затем среднее между группами. Pooled — единый RMSE всех сопоставленных точек. Два приёмника не являются независимыми поездками. Validation ранее многократно использовался, поэтому это не новый независимый test и не официальный score.

## Одинаковые искусственные отказы

Group-macro RMSE именно внутри event-окон. Команда управления остаётся доступной, в том числе при dropout обоих wheel sensors.

| Сценарий | Наш v8, м/с | Peer mean, м/с |
|---|---:|---:|
| Передняя тележка +5 м/с на 5 с | **0.414421** | 2.709636 |
| Обе колёсные скорости пропали на 5 с | **0.558804** | 1.991759 |
| Обе колёсные скорости пропали на 10 с | **0.723734** | 3.352763 |
| Обе тележки сообщают ноль 3 с | **0.456188** | 5.428077 |
| Общее резкое +5 м/с, 0.7/1.2 с | **0.063562** | 4.804238 |
| Плавный одинаковый дрейф обоих каналов | 3.071476 | **3.060703** |

Четыре исходных вида отказов: 76 сценариев, 120 сравнений с reference. Их общий group-macro event RMSE **0.538287** у v8 и **3.370559** у mean (-84.03%). Дополнительные abrupt/slow suites по 38 сценариев каждая не смешаны в эту цифру. Использованы прежние vehicle-only anchors из неизменённого H13 evidence, а не моменты, выбранные по ошибкам текущего сравнения.

При отказе только передней тележки peer front имеет event RMSE 5.104388, peer rear 0.426609 м/с. Выбор одного канала не является универсальным решением: нужен выбор по надёжности.

### Наше слабое место

Плавный common-mode drift обманывает и v8, и mean. У example smoothing event RMSE 2.950812 м/с, у v8 3.071476 м/с, но обе ошибки велики. После конца такой инъекции среднее подтверждённое recovery: **4.4075 с у нас**, **0.3616 с у mean**, **1.5233 с у smoothing**. Это реальный компромисс защитных порогов/адаптации; не заявляется превосходство по всем сценариям.

## Чувствительность к планировщику

После первичного результата выполнен отдельный прогон через **неизменный EventClock товарища** с исходными SQLite receipt timestamps и header stamps. Все пять методов работают на общей целочисленной 50-мс сетке, теперь построенной его scheduler. OurAdapter только приводит интерфейс нашего неизменного core к update/predict, буферизуя будущие header samples; параметры не меняются.

На всех 19 validation-bag:

| Оцениватель | Group-macro RMSE, м/с | Pooled RMSE, м/с |
|---|---:|---:|
| v8 | **0.115758** | **0.217048** |
| Peer mean | 0.183248 | 0.349105 |
| Peer front | 0.133329 | 0.222984 |

n=698667. Вывод не перевернулся. Минимальная доля тактов с доступной оценкой среди bag: v8 99.9695%, mean 99.9950%; более поздняя инициализация не скрыта. Это post-primary timing sensitivity, не native ROS latency или новый независимый test.

## Что стоит взять у товарища

Единый reset/update/predict API, явное разделение stamp_ns/received_ns, int64 EventClock, повторение callback-трассы, кеш CDR по hash, SHA-группы точных дубликатов, drop/delay/spike/freeze/scale и HTML/CSV-отчёты. Это полезная инфраструктура для независимого прогона нашего observer. Его README честно называет текущие алгоритмы базами; идеи из IDEAS.md нельзя считать уже реализованными.

Наш алгоритм уже содержит нелинейную модель тяги/торможения, прогноз при недостоверной одометрии, раздельные gates, адаптацию и защиту от части общих аномалий. Peer mean только усредняет последние скорости; stale даёт предупреждение, но продолжает удержание без модели движения.

## Почему старые README-цифры не сравнимы напрямую

Peer 0.04719 и 0.06424 м/с относятся к двум другим конкретным bag. Его evaluator выбирает master при наличии потока, иначе rover; здесь оба receivers сохраняются отдельно. Различаются набор, clock, маски и агрегация. Сравнение 0.11455 и 0.04719 без этих условий некорректно.

Peer p95 17.96 мс — авторский замер callback→publish на коротком bag при playback×2, без доставки до callback. Это не тот же endpoint, что end-to-end до независимых подписчиков. Нового ROS latency/RSS benchmark обоих приложений в этой работе нет. Числа из его VALIDATION.md не выданы за независимо воспроизведённые измерения.

## Решение

**Оставить main на v8. Не заменять его средним колёс и ничего не сливать автоматически.** Следующий полезный интеграционный эксперимент — наш observer в лабораторном API товарища на новых согласованных записях; slow common-mode recovery требует отдельной доработки. Такой интеграции/merge здесь не выполнялось.

Полный архив сравнения, выданный в чате, содержит JSON/CSV всех bag и сценариев, source hashes, скрипты обоих прогонов и логи. Приватный исходный код товарища не перепубликуется; для воспроизведения нужен доступ к его закреплённому checkout. Основной прогон повторён после упаковки скрипта без изменения модели, с проверкой совпадения результатов.
