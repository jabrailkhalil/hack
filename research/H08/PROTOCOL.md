# H08 — предварительно зарегистрированный протокол

Baseline: `984fdf2fc4faf05325249215d6b8541c0e68209a`, профиль `adaptive_v5`. Ветка: `research/parallel-H08`. Протокол фиксируется до реализации и любых новых измерений. Main, чужие ветки, опубликованные отчёты и historical final test не изменяются. Merge и auto-merge запрещены.

## Механизм и ровно один вариант

Baseline сначала вычисляет конечное состояние инерционного привода `d1=T+(d0-T)*exp(-h/tau)`, затем использует `h*d1` вместо интеграла привода. Сопротивление вычисляется в начале шага. На переходах это может создавать численную ошибку, которую disturbance-адаптация частично компенсирует, но при отказе колёс компенсация перестаёт обновляться.

Единственный кандидат `h08_exact_midpoint`: удерживать существующий target `T=drive_target(u,v0)` на шаге; аналитически интегрировать вклад привода; оценить скорость в середине шага по точному полушаговому интегралу привода и начальному сопротивлению; использовать сопротивление в этой предсказанной средней точке для полного шага. Сохранить конечное состояние привода для существующей адаптации. Ограничения ускорения, скорости и запрет смены знака при выбеге/торможении сохраняются. Интегрирование дистанции остаётся существующей трапецией по скоростям после коррекции — отдельный новый способ коррекции дистанции не исследуется.

Формулы: `phi(x)=(1-exp(-x))/x`, `mean_drive(h)=T+(d0-T)*phi(h/tau)`. Для малых аргументов использовать expm1/ряд, чтобы не терять точность. `v_mid=v0+h/2*clip(mean_drive(h/2)-resistance(v0)+b)`, затем `v_pred=v0+h*clip(mean_drive(h)-resistance(v_mid)+b)`. Средняя скорость ограничивается существующим max_speed. Конечный drive рассчитывается аналитически. Это точный интеграл только при удерживаемом target, не точное решение всей нелинейной системы.

Новых настраиваемых физических/фильтровых коэффициентов нет. Только бинарное opt-in включение метода; при выключении исполняется прежний численный путь. Максимум один кандидат, никаких дополнительных вариантов после просмотра метрик. Значения mass, force, tau, adaptation, Q/R, gates, recovery, scales и timeline из baseline сохраняются.

## Предыдущие отрицательные результаты и риски

Прочитаны `reports/research_v6/REPORT.md`, `reports/research_v5/REPORT.md`, текущий core и evaluator. V6 projection/decay улучшали clean, но ухудшали fault RMSE сверх допуска; V5 noise/adaptation variants также имели отрицательные результаты. Эти изменения не повторяются. Особый риск H08: физические коэффициенты ранее оценены с дискретной моделью, а disturbance обучается по конечному drive; меньшая ошибка интегрирования сама по себе не гарантирует лучшую реальную одометрию. Активный quadratic drag практически нулевой, поэтому эффект сопротивления может быть небольшим вне окрестности нуля.

## Данные, порядок и блокировка test

1. Unit/аналитические тесты и bounded-memory/causality checks — только корректность реализации.
2. Development использует исключительно `Store.load(bag, 'train')` и разрешённые controller/front/rear. Loader train не читает GNSS. Выполняются реальные replay, проверка одинакового расписания, конечности, причинности и измерение вычислительной стоимости. Параметры и выбор кандидата по этим данным не подбираются. Без независимого reference не заявлять train speed/distance accuracy.
3. До validation сохранить отдельный `FROZEN.json` с SHA кандидата, hashes кода, evaluator, split, profile и протокола. Отсутствие development данных/ошибка реализации блокирует validation; механические исправления допустимы до freeze и протоколируются, расширение поиска запрещено.
4. Validation: все исходные validation-bag из неизменного `research/plan_v3.json`, оба GNSS reference доступны только evaluator. Никогда не передавать reference алгоритму. Historical final test и его метрики не открывать и не использовать; `FinalStore` и authorize-final-test не вызываются.

## Один неизменный измеритель

Использовать без изменения `tools/finalization/evaluate.py` (score/replay/reference matching/distance), `tools/research_v3/experiment.py` и `tools/research_v6/compare.py` (summary/decide). Одни events, stamps, reference-маски и fault-окна для v4 контрольного воспроизведения, baseline adaptive_v5 и H08. Fault locations и виды: буквально существующий алгоритм v6 (bias 5s, dropout 5/10s, lock 3s). До сравнения проверить SHA evaluator-файлов против закреплённого baseline. В validation повторить `reproduce_published_v5`, не выдавать прошлые цифры за новые.

Сохранить raw JSON результатов, все per-bag/per-receiver метрики, aggregate, access journal, версии среды, run_id/run_attempt. Новая директория и checkpoint-ветка с H08 и run/attempt; не перезаписывать старые отчёты. Вычислительная стоимость: development paired replay на одинаковых inputs, повторения в чередующемся порядке; отдельно wall/CPU на output и real-time factor. Это не ROS publisher latency и не доказательство ограничений на целевом оборудовании. ROS 20Hz/latency/2CPU/500MB проверять отдельно при доступной среде.

## Неизменные критерии опровержения

Не менее 2% улучшения clean group-macro RMSE ИЛИ 5% fault-event group-macro RMSE против adaptive_v5. Регрессия каждой основной агрегированной ошибки скорости (clean/fault/pooled) не более 0.5%, дистанционной не более 1%. Per-bag/per-receiver clean RMSE не хуже baseline более чем на max(0.005 m/s, 5%). Нет потери n/coverage, дополнительных false-stop samples, unrecovered faults, причинностных ошибок или неожиданных reset. Исходный v6 decide используется неизменным, дополнительно контролируется явное требование pooled <=0.5%; не ослаблять проверки.

Не прошедший accuracy/safety gate кандидат — отрицательный исследовательский результат, не готов к merge. Недоступные данные/вычисление/запись означают `недостаточно данных`, а не выдуманный PASS/FAIL. Даже прошедший повторно использованный validation не является независимым final test. Принятие для deployment требует отдельной проверки runtime-ресурсов и latency; отсутствие такой проверки указывать явно.
