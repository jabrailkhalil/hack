# H05 — предварительный протокол, до экспериментов

Статус: зарегистрирована одна гипотеза; результатов нового кандидата пока нет.
Ветка: `research/parallel-H05`. Общий baseline: `984fdf2fc4faf05325249215d6b8541c0e68209a`, профиль `adaptive_v5`. Main, чужие ветки, опубликованные отчёты, final test и submission не изменяются. Merge и auto-merge запрещены.

## Механизм и границы

Текущий Observer после instantaneous gate сразу возвращает принятому колесу полный вес. Проверяется конечная история **приписываемых конкретному каналу** аномалий. Для front/rear отдельно хранятся не более четырёх последних anomaly timestamps и последний обработанный timestamp. Вес события линейно убывает до нуля за 2 секунды; события старше окна удаляются. Надёжность q = max(0.25, 1 / (1 + sum(max(0, 1 - age/2)))). Один хороший sample историю не обнуляет; спустя 2 секунды без новых аномалий вес точно равен 1. Это не hard blacklist.

Аномалии: свежий уникальный RANGE или RATE_ANOMALY; MODEL_DISAGREEMENT/AMBIGUOUS_PAIR только если второй канал принят в том же tick. Повторный, старый, будущий, отсутствующий/stale sample и общее расхождение обоих колёс с моделью не являются отдельным доказательством неисправности канала. События дедуплицируются по sensor timestamp. Общий модельный drift не должен замкнуть контур самоподтверждающегося недоверия.

Меняется только формирование принятого wheel measurement: z = sum(q_i*z_i)/sum(q_i); базовая R (включая существующий множитель для single wheel) делится на среднюю q принятых каналов, затем применяется прежнее residual inflation. Никакого 1/N выигрыша дисперсии от предполагаемой независимости двух колёс. При q=1 используется исходная арифметическая ветка для точного воспроизведения baseline. Instantaneous gates, disturbance adaptation, bootstrap, bounded reacquisition, stop logic, Timeline и ROS adapter не меняются. Это также ограничение: disturbance по-прежнему использует исходную согласованную пару.

## Единственный вариант и остановка поиска

`H05_ttl2s`: window=2.0 s, minimum reliability=0.25, максимум 4 события на канал. Других значений, комбинаций и адаптивного второго раунда в этом исследовании нет. При отсутствии эффекта или регрессии вариант отклоняется; параметры по validation не меняются. Эти значения выбраны до чтения новых измерений, не подобраны на историческом final test.

До validation фиксируются patch SHA256, baseline, config и evaluator identity в `research/H05/FREEZE.json`, отдельным от первоначального протокола коммитом. Реализация может быть исправлена по unit/invariant-тестам до заморозки; изменение после просмотра validation требует новой гипотезы, а не замены этого результата.

## Development/train и validation

Не расширять права legacy Store: train читает только controller/front/rear; GNSS train недоступен по опубликованному контракту. Перед validation — одинаковый replay baseline/candidate на первых трёх train-bag из закреплённого plan_v3: `30618_0259fe53`, `30618_082f1d65`, `30618_095a115b`. Это проверки исполнения/причинности/расписания, НЕ оценка абсолютной точности. Подбора параметров нет. Unit-тесты и искусственные последовательности также не являются доказательством выигрыша на реальных записях.

Затем ровно один validation-прогон замороженного кандидата на всех 19 validation-bag с обоими GNSS receivers только у offline evaluator. Использовать неизменные `tools/finalization/evaluate.py`, `tools/research_v3/experiment.py`, `tools/research_v6/compare.py`, split/plan/exporter/timeline от baseline. Переиспользовать score, match, metrics, distance_surrogate, validate_bag/fault placement, summary и decide, не переписывая их определения. Разрешена только явная подстановка реализаций Observer/configurations в исследовательском driver. Сам baseline Observer загружается из закреплённого git-объекта, а не объявляется эквивалентным кандидату с выключенным флагом. Дополнительный v4 служит только проверке воспроизведения прежнего evaluator; сравнение H05 проводится с adaptive_v5.

Общие 20 Hz, alignment delay=0, одинаковые данные/stamps/reference masks, опубликованные 76 fault-сценариев (front bias +5 m/s на 5 s, both dropout 5/10 s, both lock 3 s), все исходные per-bag/per-receiver результаты, access journal и отсутствие test IO. Восстановление baseline сверяется с опубликованным v5, но старые числа не выдаются за измерения H05. Повторно используемый validation НЕ является независимым final test.

## Неизменные критерии опровержения

Кандидат не проходит, если нет >=2% clean group-macro RMSE gain И нет >=5% fault-event group-macro RMSE gain относительно adaptive_v5; либо если clean или fault агрегат регрессирует >0.5%, distance RMSE >1%, per-bag/receiver clean RMSE > baseline + max(0.005 m/s, 5% baseline). Дополнительно явно проверяется pooled RMSE <= baseline*1.005, в соответствии с требованием об основных агрегатах. Нельзя терять coverage/сопоставленные точки, добавлять false stops или unrecovered cases, менять расписание либо нарушать причинность/reset contract. Пороги не смягчаются по результатам. Все существенные регрессии публикуются, включая случаи, где другая метрика улучшилась.

Для отрицательного решения достаточно нарушения любого gate. Подтверждение точности требует реальных paired validation измерений; unit tests, старые отчёты и успешный build недостаточны. При недоступных данных/исполнении итог — «недостаточно данных», а не фиктивное подтверждение или опровержение. Runtime на ROS и 2 CPU / 500 MB требует отдельной фактической проверки: dependency-free тесты её не заменяют.

## Предыдущие отрицательные результаты

Изучены reports/research_v6/REPORT.md и reports/research_v5/REPORT.md на общем baseline. v6 projection и disturbance decay дали недопустимые fault-регрессии даже при clean gain; затухание disturbance не повторяется. В v5 увеличение process noise добавляло false stops; process noise не меняется. Исторический reacquisition-кандидат уже покрыт v4 — исправление того же бага не считается новой H05. Нельзя использовать текущее согласие как независимый абсолютный anchor или наказывать оба колеса только за drift модели.
