# H04 — протокол до экспериментов

## Baseline и область изменений

Baseline: `984fdf2fc4faf05325249215d6b8541c0e68209a`, профиль `adaptive_v5` (`adaptation_tau_s=0.5`). Ветка: `research/parallel-H04`. Main, другие исследовательские ветки, опубликованные отчёты и final test не меняются. Merge/auto-merge запрещены.

Изучены `reports/research_v5/REPORT.md`, `reports/research_v6/REPORT.md`, действующий core и неизменные evaluator/Store. В v5 постоянная tau=0.25 не прошла отбор; это аргумент ПРОТИВ постоянного ускорения. В v6 затухание disturbance после потери доверия ухудшало fault RMSE. H04 не переносит измерения по времени, не меняет оценку ускорения и не ослабляет удерживаемую disturbance во время отказа.

## Механизм и конечный бюджет

Ровно **один** кандидат `h04_regime_quality_v1`; никаких дополнительных вариантов и перебора после просмотра метрик. Параметры заданы априори, не подбираются на validation.

Существующее обновление disturbance, разностная оценка ускорения, ограничения, колесные/model gates и восстановление сохраняются. Меняется только tau в `1-exp(-dt_pair/tau)`:

* Базовая tau = 0.5 с.
* Быстрая tau = 0.25 с (0.5 × baseline tau) только в пределах 0.75 с после смены traction/coast/brake, при сильном качестве пары и не менее 0.20 с непрерывного доверия.
* Медленная tau = 2.0 с (4 × baseline tau) при пограничном качестве или в течение 0.50 с после обнаруженного ухудшения данных.

Режим: u > command_deadband — traction; u < -command_deadband — brake; иначе coast. Первое наблюдение режима не является переходом. Классификация использует текущий причинный command.

Сильное качество: две новые принятые согласованные пары; возраст каждого измерения <=0.10 с, skew <=0.05 с, расхождение скоростей <=0.15 м/с, отклонение средней колесной скорости от уже вычисленного predicted <=max(0.30 м/с, 3*wheel_sigma_mps). Проверки качества не меняют Kalman correction или evaluator.

Недостоверная/просроченная команда и жёсткий статус колеса (любой кроме ACCEPTED/DUPLICATE_OR_OLD) сбрасывают доверие и запрещают быструю адаптацию на 0.50 с. Тики с удерживаемыми дубликатами не считаются новыми измерениями, не продлевают переход и сами по себе не являются отказом. Без валидной FUSED-пары существующее обучение остаётся выключенным; disturbance удерживается без decay. Дополнительное состояние — фиксированное число скаляров, O(1), без новых очередей.

## Порядок и разделение данных

1. Этот протокол коммитится до исполнения экспериментов.
2. Реализуется один кандидат; фиксируются его config и исходники. Unit/mechanism tests не считаются доказательством реальной точности.
3. Development = существующий split `train`, через неизменный `experiment.Store.load(bag, 'train')`: только controller/front/rear, без GNSS/IMU. Проверяются исполнимость, причинность и покрытия режимов. Отсутствующие reference-метрики остаются null, не нулями. Никакого открытия final-test SQLite.
4. Перед единственным validation кандидат замораживается commit SHA и SHA256 исходников/config/протокола в `FROZEN.json`. Исходники evaluator и split должны совпадать с baseline. При ошибке инфраструктуры допустим повтор того же frozen-кандидата; изменение параметров после validation запрещено.
5. Validation использует ровно тот же `evaluate.score`, `replay`, timestamps/reference masks, оба GNSS-приёмника (только offline scoring), fault locations/durations и `research_v6.compare.summary/decide`, что baseline. v4 может быть воспроизведён только как контроль исторической воспроизводимости; точка сравнения H04 — v5.
6. Все результаты и access journal сохраняются отдельно, с H04/run_id/run_attempt. Final test не запускается. Повторно используемый validation не является новым независимым final test.

## Критерии опровержения (не менять после цифр)

Минимум 2% улучшения clean group-macro RMSE ИЛИ 5% fault-event group-macro RMSE относительно v5. Не более 0.5% регрессии каждой основной агрегированной метрики скорости (в том числе pooled RMSE) и 1% scalar span distance RMSE. Per-bag/receiver clean RMSE <= baseline + max(0.005 м/с, 5%). Без потери coverage/числа точек, дополнительных false stops, невосстановлений, причинных ошибок или неожиданных resets. Существующий `decide` вызывается без изменений; если он не проверяет pooled RMSE, этот уже заявленный дополнительный запрет проверяется отдельно, не вместо исходных gates.

Любое нарушение => кандидат отвергнут, даже при clean gain. Отсутствие нужных данных или завершённой проверки => недостаточно данных. Неподтверждённый PR явно помечается «исследовательский отрицательный результат / не готов к merge»; это не приравнивается к доказанному ухудшению.

20 Гц, нулевая искусственная задержка, три runtime vehicle-топика, существующие лимиты памяти/CPU сохраняются. Полный ROS/resource/latency прогон нужен для заявления соответствия runtime; Python-тесты его не заменяют.
