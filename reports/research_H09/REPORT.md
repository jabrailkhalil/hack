# H09 — отрицательный исследовательский результат, не готово к merge

## Решение

**Проверенный вариант H09 отвергнут на development.** Сокращение накопления дистанции на reference-low-speed отрезках не компенсирует дополнительные ложные остановки. Общие пороги улучшения RMSE также не достигнуты. Параметры после просмотра результатов не менялись; новых вариантов не добавляли.

Validation **не запускался**: заранее записанное правило запрещает переход после development safety-регрессии. Кандидат для validation не выбран и не заморожен. Final-test payloads и исторические final-test показатели не использовались. Это отрицательный результат одного конкретного механизма, а не доказательство невозможности всех подходов к H09.

Рабочая ветка: `research/parallel-H09`. Baseline: `984fdf2fc4faf05325249215d6b8541c0e68209a`, профиль `adaptive_v5`. Коммит алгоритма и измерителя: `5d1c50ada7a9e7e4d3885b1329ffc15d60258477`. План закреплён **до экспериментов** коммитом `ef1e94de68ef74cc37dcd0eadf5e355c34137f0d`: [PLAN.json](../../research/parallel/H09/PLAN.json).

Main, чужие ветки и опубликованные отчёты не изменялись. Merge и auto-merge не выполнялись. Как у отвергнутых вариантов v6, активный `core.py` и default сохранены: реальное изменение ядра находится в [core.patch](../../research/parallel/H09/core.patch), новый компонент — в [stop_history.py](../../src/reserve_odometry/reserve_odometry/stop_history.py). Runner применяет патч в отдельной временной копии и действительно исполняет изменённый Observer. Это не тестирование неизменного baseline под новым названием.

## Механизм и учтённые отрицательные результаты

Исходный алгоритм объявляет остановку после 0,5 с непрерывного подтверждения свежими удерживаемыми колёсными значениями <0,07 м/с при отсутствии тяги и модельной скорости <0,25 м/с. Изучены `reports/research_v6/REPORT.md`, `reports/research_v5/REPORT.md`, код stop/reacquire/adaptation и evaluator. В v5 увеличение process noise ×4 уже добавляло ложные остановки; варианты projection/decay v6 нарушали fault-регрессионный порог. Поэтому общие model/reacquire gates не ослаблялись.

Зарегистрирован и проверен ровно **один** вариант:

- Вход: минимум три разные принятые моделью front/rear-пары, охватывающие ≥0,20 с; каждое колесо <0,02 м/с; предкоррекционная модельная скорость <0,10 м/с.
- Удержание: оба доверенных колеса <0,05 м/с; прежний model stop guard <0,25 м/с сохраняется. Удерживаемые samples поддерживают уже подтверждённую остановку, но не дают новых голосов.
- Немедленная отмена при тяге, stale/invalid/future/rejected данных, нарушении skew или порогов скорости. История подтверждений ограничена `max_age_s`; reset очищает её. Чередующиеся front/rear arrivals поддерживаются без повторного засчитывания одного sample.

Новый компонент использует постоянное число полей и два двухэлементных массива: O(1) память, счётчик насыщается на трёх. Только controller/front/rear, без GNSS/IMU и будущих samples. Физика, коэффициенты, disturbance adaptation, интегрирование дистанции и Timeline не менялись. Выход остаётся 20 Гц, `alignment_delay_s=0`. В экспериментальном патче старый `stop_dwell_s` заменён фиксированным механизмом подтверждений; это не новый подбор физической конфигурации.

## Методика и изоляция данных

Использованы все **17 development-bag / 7 групп** из неизменного split; reference доступен в 6 группах и 19 bag/receiver-парах. Оба приёмника сохранены. Семь bag без сопоставленного reference не превращаются в нулевую ошибку. Имеется 56 детерминированных fault-сценариев и 60 fault/receiver-сравнений с reference в event-окне.

Первый локальный прогон использовал проверенный экспорт development. [Export run 36174399106](https://github.com/jabrailkhalil/hack/actions/runs/36174399106) проверил SHA256 датасета и каждого bag, membership development и whitelist тем до read-only SQLite IO. Второй прогон в [Actions 36175737653](https://github.com/jabrailkhalil/hack/actions/runs/36175737653) повторил измерение непосредственно из проверенных development DB. Скачать и распаковать контейнеры общего архива — не то же самое, что открыть test SQLite payloads; последние не открывались.

Общий измеритель **не изменён**: `tools/finalization/evaluate.py` (score, replay, distance), `tools/research_v3/experiment.py` (match/metrics) и group-macro функции `tools/research_v6/compare.py`. SHA256 evaluator, Timeline, split, конфигураций и baseline core проверяются по [EVALUATOR_LOCK.json](../../research/parallel/H09/EVALUATOR_LOCK.json) и точному baseline до/после прогона. Меняется только фабрика Observer по классу конфигурации: исходный baseline либо реально применённый H09-патч. `asdict(config)` у них совпадает.

В сырых данных старые обязательные evaluator aliases сохранены: **`baseline_v2` означает adaptive_v5 baseline**, **`balanced_physics` означает H09**, а не исторические модели v2/v3. Все таблицы этого отчёта используют правильные смысловые названия.

Одинаковые массивы входов, timestamps, reference-маски и operational settings используются для обоих алгоритмов. Fault-anchor и окна скопированы без изменений из v6: первый допустимый grid sample со средней колёсной скоростью >2 м/с, t>max(25 с, 10% длительности) и t<duration−25 с; bias переднего колеса +5 м/с на 5 с, dropout обоих 5/10 с, zero-lock обоих 3 с. Общий false-stop счётчик использует reference >1 м/с и исходное окно до fault-end+10 с.

До измерений дополнительно зарегистрированы STOPPED-счётчики при reference (0,07;0,50] и (0,50;1,00] м/с, чтобы не скрыть медленное движение за исходным порогом >1. Они не заменяют общие метрики. Прокси накопления дистанции: сумма абсолютных приращений s на непрерывных ≥1 с отрезках с matched reference ≤0,03 м/с. Это GNSS-speed proxy, **не разметка истинных остановок**. Receiver-wise spans и samples не являются независимыми физическими эпизодами.

Пороги сохранены: ≥2% clean RMSE gain **или** ≥5% fault RMSE gain; ≤0,5% регрессии каждой основной агрегированной метрики (также проверен pooled RMSE), ≤1% агрегированной дистанционной; per-bag clean ≤max(0,005 м/с, 5% baseline); отсутствие потери coverage, дополнительных false stops, невосстановлений, causality errors и unexpected resets. Дополнительный H09 safety-gate запрещает рост low-speed STOPPED per bag/receiver. Ничего не смягчалось после получения цифр.

## Воспроизведение

Обычный полный checkout, где доступен baseline commit:

```bash
git fetch origin
git switch research/parallel-H09
python -m pip install -r requirements-research.txt
python tools/get_dataset.py
PYTHONPATH=src/reserve_odometry python -m unittest discover -s tests -v
PYTHONPATH=src/reserve_odometry python -m unittest discover \
  -s research/parallel/H09 -p 'test_*.py' -v
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python tools/research_h09/compare.py \
  --stage development --output /tmp/h09-new-development-run
```

Output должен быть новым. Runner сам применяет патч в отдельной копии; не применять его к активному core перед сравнением. Команды тестирования существующих сценариев с временно активированным H09 и последующим restore находятся в [workflow](../../.github/workflows/h09-development.yml). Параметров поиска и final-test stage нет.

Фактическая локальная команда (проверенный export и точные baseline source bytes):

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python tools/research_h09/compare.py \
  --stage development --baseline-root /mnt/data/h09-baseline \
  --inputs /mnt/data/h09-inputs --output /mnt/data/h09-development-run1
python /mnt/data/h09-work/benchmark.py
```

Validation этой ветки запускать нельзя: `development_safety_passed=false`. Зафиксирован [SELECTION.json](SELECTION.json) с отказом и отсутствием выбранного validation-кандидата. Не создавать положительный FREEZE на основании этих данных.
