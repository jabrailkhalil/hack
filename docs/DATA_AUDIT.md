## Критическое расхождение единиц

README §4.1 называет wheel velocity скоростью в м/с. При сопоставлении с горизонтальной нормой GNSS velocity получено:

| Bag | Приёмник | Число front/GNSS пар | Медиана raw_front / GNSS | MAE после /3.6, м/с |
|---|---|---:|---:|---:|
| 30618_0652866c | master | 7992 | 3.595258 | 0.029144 |
| 30618_27e994fc | master | 7366 | 3.575561 | около 0.060 |
| 30639_9c362687 | master | 7213 | 3.624315 | около 0.055 |
| 30639_c31df386 | master | 6493 | 3.633715 | около 0.062 |
| 30639_e4379d7f | rover | 3014 | 3.626438 | около 0.056 |

Метод: ближайшие header.stamp до 50 мс; GNSS speed = hypot(linear.x, linear.y); движение >2 м/с; сравнение отдельных front и rear каналов с обоими приёмниками, где есть данные. Полный машинный отчёт: [smoke_data_audit.json](../reports/smoke_data_audit.json).

Вывод **по наблюдениям**: значения похожи на км/ч, а не м/с. Это не официальное исправление README и не доказательство единиц всех скрытых записей. Default scale=1/3.6 задаётся явно и одинаково для обоих каналов; runtime не вычисляет его из GNSS. Уточнить также знак скорости и систему координат GNSS TwistStamped, особенно для заднего хода.

## Топики и временные метки

В `30618_e151d6e4` экспорт содержит только три vehicle-топика, GNSS-метрики для него отсутствуют. В `30639_e4379d7f` есть rover, но нет master GNSS-сообщений. Это не подтверждает утверждение README о семи топиках в каждом прогоне. Нельзя считать отсутствие GNSS нулевой ошибкой модели.

В исследованных длинных записях интервалы wheel header.stamp обычно около 0.1 с, controller около 0.05 с. Время записи SQLite и header.stamp различается; встречается стартовый backlog с секундными задержками, до примерно 6.25 с в выбранных данных. Поэтому нельзя интегрировать по порядковому номеру сообщения или wall clock. При offline replay сохраняется порядок `timestamp,id`, а наблюдатель принимает только причинные по времени samples.

Существующий Timeline открывает новый относительный сегмент на большом скачке. В smoke зафиксирован один стартовый reset в каждом bag и дополнительный reset в `30639_9c362687`. Это открытая инженерная проблема для непрерывной оценки положения, а не исправленный дефект данных.

## Координатный контракт: блокер 35 баллов за положение

PDF, страница 5, допускает дистанцию вдоль пути, координаты pathgraph и относительную одометрию. README §5.1 требует метрические xyz, согласованные с GNSS, и 3D-сравнение. Эти режимы не эквивалентны на поворотах.

Передняя/задняя тележки дают продольную скорость, а не yaw. Поэтому `(s,0,0)` нельзя называть реконструированной GNSS-траекторией. Начальная позиция не определяет дальнейшие повороты. Готовая карта и система координат судьи в исследованном составе не подтверждены. Реализован путь решения при разрешённой карте: интегрировать s и интерполировать известный ordered route; загрузчик карты не создаёт её из test GNSS.

## Совместимость исходного message package

Wire-определения двух `.msg` сохранены. В предоставленном package.xml не было maintainer; в CMakeLists явно добавлен `find_package(ament_cmake REQUIRED)`. Это изменения build metadata, не типов сообщений. Сборка обоих пакетов в Humble уже прошла в CI. Оригинальный package.xml декларирует MIT для tram_vehicle_msgs; это не означает автоматически MIT для всей документации/датасета или нашего проекта.

## Что делать с результатом

Отправить вопросы организатору. До получения ответа не усложнять физическую модель ради компенсации ошибки масштаба и не тратить время на «предсказание поворота» из разности front/rear. Перечень доказательств и точные команды воспроизведения оставить рядом с каждым изменением контракта.
