## Что теперь используется

`src/reserve_odometry/config/default.yaml` совпадает с экспортом выбранной `balanced_physics`. Идентичность конфигурации выбранному допустимому кандидату проверяется unit-тестом. `calibrated_v3.yaml` - именованная копия для явного запуска. Все четыре кандидата, включая старый baseline, сохранены в `config/candidates_v3/`.

Базовый `Config()` в Python оставлен неизменным: он нужен для сравнения с v2. Поэтому использовать `ros2 launch reserve_odometry odometry.launch.py` либо передавать `--params-file` при прямом `ros2 run`. Ручное копирование обученных коэффициентов в core.py сломает смысл baseline следующего эксперимента.

Параметры массы 40000 кг, радиуса 0.33 м, КПД 0.9 и передачи 6 задают фиксированную нормировку. Подбираются их эффективные комбинации с силами/моментом, а не каждый физический параметр независимо. Обучение не доказывает паспортные характеристики реального трамвая.

## Исследовательский пайплайн

Фиксация плана -> metadata-only группировка -> train-only fitting -> validation всех кандидатов на одинаковых временных сетках -> четыре заданных fault-сценария -> заранее заданные критерии принятия -> отчёт и config -> отдельный ROS CI.

Manifest объединяет записи с пересечением record/source timestamps, соседством до 60 секунд и точными дубликатами. Все группы с прежними smoke-прогонами отнесены к development. Разделение закреплено SHA256, а Store проверяет принадлежность bag к train/validation до открытия измерений. Test не запускается автоматически и не предоставлен fitter/evaluator.

GNSS используется только как эталон validation; train загружает три vehicle-топика. Симметричное сглаживание при построении train target не применяется к runtime. Программная блокировка test не защищает от владельца, который намеренно перепишет evaluator: это дисциплина воспроизводимого исследования, не криптографическая изоляция.

## Как повторить

ROS-сборку выполнять системным Python 3.10 в Humble. Научный fitting - отдельным Python 3.13 окружением по командам отчёта. До отключения сети заранее получить датасет и установить зависимости. Runtime не импортирует SciPy/numpy и не скачивает модели.

Чтобы сравнить модель с прежней:

```bash
ros2 launch reserve_odometry odometry.launch.py \
  params_file:="$PWD/src/reserve_odometry/config/candidates_v3/baseline_v2.yaml"
```

Чтобы проверить фактически установленный calibrated launch:

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
python3 tests/ros_calibrated_smoke.py
```

Тест стартует launch отдельным процессом, читает объявленные model-параметры через GetParameters, сверяет их с выбранным JSON и проверяет выходные скорость/позицию по ROS-топикам. Он также проверяет отсутствие GNSS/IMU подписок. Это короткая синтетическая интеграционная проверка, не длительное измерение latency.

## Что осталось до сдачи

Подтвердить единицы, координаты/карту и правила начального GNSS у организаторов; проверить end-to-end latency и память на длительном реальном прогоне; после заморозки отдельно выполнить финальный test. 3D-ошибка и integrated speed error не эквивалентны. Issue #3 остаётся открытым до независимого финального отчёта и недостающих проверок.

Не публиковать «улучшение на всём датасете 2.23%»: это относительное изменение group-macro RMSE на заданном validation с доступным GNSS (30 bag/receiver сравнений, 9 групп с метрикой). Уменьшение ошибок внутри введённых сбоев не доказывает распознавание любого общего проскальзывания.
