# Решение: причинный наблюдатель скорости + координата вдоль пути

## 1. Что реализовано, а что является следующим этапом

Реализованы нелинейная модель привода, продольная динамика, проверка двух колёсных каналов по отдельности, скалярная робастная коррекция скорости, ограниченная онлайн-адаптация возмущения, интегрирование расстояния, ROS 2 Humble-адаптер и проекция на **явно заданный упорядоченный маршрут**. Это исполняемый baseline, не завершённая система навигации.

Не реализованы: автоматическое определение маршрута/стрелок, GNSS-инициализатор, идентификация физических параметров на train, гарантированное восстановление после длительного общего юза, полноценная ковариация состояния и подтверждённая 3D-точность. Эти пункты нельзя обозначать выполненными в презентации.

Основной контур подписан только на три `/vehicle/*` топика. GNSS находится только в offline-аудите и расчёте метрик. Включение карты не даёт права подставлять будущую GNSS-траекторию проверочного прогона.

## 2. Почему именно такая архитектура

По PDF за скорость дают 30 баллов, положение 35, устойчивость 20, производительность 15. Поэтому первый приоритет не нейросеть, а правильные единицы, время, контракт топиков, небольшой bias скорости и корректная геометрия положения.

```
controller / front / rear
          |
  typed adapter: units, timestamps, validation
          |
  bounded causal queues + 20 Hz time grid
          |
  nonlinear traction/braking + longitudinal prediction
          |
  independent wheel gates + robust velocity correction
          |
  trusted-only disturbance adaptation
          |
  v, acceleration, s, uncertainty, diagnostic states
          |
  optional authorized route r(s0+s) -> xyz + orientation
          |
  /result/velocity, /result/position, /result/diagnostics
```

Нельзя считать переднюю и заднюю тележки левым и правым колесом дифференциального робота. Формула угловой скорости `(v_right-v_left)/track_width` здесь неприменима.

## 3. Входы и единицы

`u = position / 15`, диапазон [-1, 1]. Положительный notch означает тягу, отрицательный торможение, а не задний ход. Направление тяги задаётся отдельно `model.travel_direction = +1/-1`; автоматическое определение направления по контроллеру не заявляется.

`z_f = front_scale * raw_front`, `z_r = rear_scale * raw_rear`.

README объявляет raw-скорости в м/с, однако исследованные записи показывают коэффициент около 3.6 относительно GNSS. Поэтому в конфигурации явно стоит `1/3.6`; это **эмпирическое допущение по данной версии датасета**, которое нужно подтвердить у организаторов. Внутри модели всегда м, с, м/с, м/с², Н, Н·м, кг. Дополнительного умножения wheel velocity на радиус нет: raw не является доказанной угловой скоростью.

## 4. Нелинейная модель привода

Пусть `q(u) = [max(0, (|u|-u0)/(1-u0))]^gamma`, ограниченное [0,1]. Здесь u0 - зона нечувствительности, gamma - нелинейность контроллера.

Эффективная суммарная сила тяги:

`F_tr(u,v) = direction * q(u) * min(eta * i * T_max / r, P_max / max(|v|, 1 м/с))`, при u >= 0.

Тормозная сила:

`F_br(u,v) = -q(u) * B_max * tanh(v / v_eps)`, при u < 0.

`T_max` - суммарный эффективный момент приводов, а не неизвестный момент одного двигателя. Переход от момента к поступательному ускорению проходит через передаточное отношение i, КПД eta, радиус r и массу m. Скоростное ограничение мощности даёт нелинейную зависимость от v.

Инерция привода:

`a_drive[k] = a_drive[k-1] + (1-exp(-dt/tau)) * (F(u,v)/m - a_drive[k-1])`.

Модель не воспроизводит реальную электрическую схему конкретного трамвая: её параметры ещё не идентифицированы. Они задают проверяемую эффективную характеристику. Значения 40 т, r=0.33 м, i=6 и другие defaults - **не паспортные данные организатора**.

## 5. Продольная динамика

`R(v) = c_roll * tanh(v/v_eps) + c_quad * v * |v|`.

`a_model = clip(a_drive - R(v)/m + d, -a_max, a_max)`.

`v_prior = clip(v_previous + dt * a_model, -v_max, v_max)`.

При торможении/выбеге численное интегрирование не должно само менять знак скорости. Нулевой переход ограничивается. `d` - суммарное неизвестное ускорение: уклон, изменение загрузки и несовпадение модели. Это не отдельные оценки массы, уклона и сцепления.

Полная физическая постановка может включать `m*g*sin(theta)` и `mu*N` для ограничения сцепления. В baseline они не выделены независимо: из доступных каналов нельзя достоверно идентифицировать все эти величины одновременно. Заявлять оценку коэффициента сцепления сейчас нельзя.

## 6. Объединение модели и датчиков

Модель измерения: `z_i = v + b_i + noise_i`, где b_i включает проскальзывание и ошибку масштаба. В baseline b_i не является отдельным оцениваемым состоянием: недостоверный канал исключается или получает меньший вес.

Для каждого нового измерения проверяются:

1. Конечность значения, диапазон, допустимый возраст и отсутствие будущей временной метки относительно момента оценки.
2. Дубликаты и обратный ход времени по этому датчику. Повторная публикация оценки не означает повторное использование старого измерения.
3. Скачок скорости больше `rate_limit * dt + noise_margin`.
4. Рассогласование с моделью, порог которого увеличивается с неопределённостью, но ограничен сверху.
5. Согласованность двух тележек при близких метках времени. При спорной паре выбирается более близкий к модели канал только при выраженном преимуществе; иначе оба считаются неоднозначными.

Предсказание дисперсии скорости: `P_prior = P + Q_v*dt`, при пропавшем контроллере Q увеличивается в 4 раза.

Для принятых каналов `z` - их среднее. Их ошибки могут быть коррелированы, поэтому дисперсия не делится автоматически на число колёс. При одном принятом канале R увеличивается; большой остаток дополнительно увеличивает R.

`K = P_prior/(P_prior+R)`;
`v = v_prior + K*(z-v_prior)`;
`P = (1-K)^2*P_prior + K^2*R`.

Это скалярная Kalman-подобная коррекция с робастным весом, **не полный EKF/UKF** и не доказанно оптимальный байесовский фильтр. При отклонённых каналах используется модельный прогноз.

Режимы: `WAITING_FOR_INITIALIZATION`, `INITIALIZED`, `FUSED`, `SINGLE_WHEEL`, `MODEL_ONLY`, `REACQUIRING`, `STOPPED`. `MODEL_ONLY` между сообщениями колёс - нормальный прогноз, не обязательно проскальзывание. Причину нужно смотреть в `front_status` и `rear_status`.

## 7. Адаптация и остановки

Только при двух **новых**, согласованных, принятых колёсных измерениях и свежем контроллере оценивается производная их средней скорости. Цель адаптации:

`d_target = a_wheels - a_drive + R(v)/m`.

`d <- clip(d + beta*(d_target-d), -d_max, d_max)`, `beta = 1-exp(-dt/tau_adapt)`.

Во время аномалий и пропусков адаптация заморожена. Это предотвращает обучение на очевидной пробуксовке. Медленное одинаковое проскальзывание двух тележек всё равно может выглядеть правдоподобно: независимого эталона внутри runtime нет.

Остановка подтверждается свежими почти нулевыми показаниями обоих каналов, близкой к нулю **модельной** скоростью, отсутствием тяги и выдержкой 0.5 с. Нулевые колёса на существенной модельной скорости означают возможный юз, а не разрешение мгновенно обнулить v.

## 8. Положение и наблюдаемость

`s[k] = s[k-1] + 0.5*(v[k-1]+v[k])*dt`.

Без геометрии пути публикуется `(s,0,0)` в честно названной системе `odom_path_1d`. Это дистанция вдоль пути, **не локальная ENU-траектория**. PDF допускает такую относительную одометрию, README §5.1 требует xyz, согласованные с GNSS. Противоречие должен разрешить организатор.

Причина принципиальна: одни и те же u(t), v_front(t), v_rear(t) могут соответствовать прямому пути и повороту с тем же профилем продольной скорости. Значит, дальнейшая ориентация и xyz не определяются этими входами однозначно. Начальная GNSS-позиция/азимут не сообщает последующие повороты.

С разрешённым известным маршрутом `r(s)` задача решается как `xyz = r(s0+s)`. Реализован `Route`: CSV с x,y,z в единой метрической системе, накопленная длина 3D-сегментов, интерполяция, ориентация по касательной. Порядок прохождения стрелок и s0 должны быть заданы. Ветвление маршрута, GNSS->ENU и начальная проекция на карту ещё не реализованы. За концом карты позиция не подменяется зажатой конечной точкой: публикация position прекращается с диагностикой, velocity продолжается.

## 9. Время и ограничения текущего baseline

`Timeline` хранит не более 128 сообщений на канал. По умолчанию рассчитывает 20 Гц по времени входных сообщений с задержкой выравнивания 60 мс; измерения из будущего относительно публикуемого времени не используются. ROS timer только вызывает обработку, но не подставляет wall clock в stamp.

`input_stamp` удобен для обычного `ros2 bag play`. Когда исчезли вообще все входы, в этом режиме время не продвигается. Для проверки полного dropout использовать `ros_clock` + `/clock`.

Forward-gap теперь не создаёт новый сегмент: `Timeline` догоняет источник причинными шагами фиксированного dt и сохраняет накопленную `s`. Backward clock jump трактуется как seek и открывает новый сегмент. На восьми development-bag повторный replay дал **0 forward resets** вместо прежних стартовых сбросов и дополнительного сброса в `30639_9c362687`.

Для длительного общего рассогласования добавлен bounded reacquisition. Он требует двух свежих согласованных тележек, выдержки 0.8 с, правдоподобной производной пары и ограниченного residual; пара около нуля не может перетянуть движущуюся модель в остановку. Коррекция ограничена 0.15 м/с на новое подтверждённое измерение и не участвует в online-adaptation disturbance. Короткий общий скачок не проходит выдержку. Это эвристика восстановления, а не доказательство, что одинаковая ошибка двух датчиков всегда распознаётся.

Остаются ограничения: в `input_stamp` при полном исчезновении всех топиков модельное время физически не может продвигаться; для такого теста нужен `ros_clock`. Ковариация положения остаётся консервативной эвристикой накопления коррелированной ошибки. Нода не является сертифицированным компонентом безопасности.

## 10. Следующая версия модели

Сначала зафиксировать train/validation/test по целым прогонам и проверить единицы. Затем по чистым участкам train оценить эффективные `F/m`, `B/m`, `P/m`, сопротивление и tau. Не пытаться одновременно свободно обучать массу, момент, радиус, КПД и масштаб: разные комбинации дают одинаковую динамику. Начать с ограниченной робастной регрессии/таблицы notch x speed и сравнить с текущей аналитической моделью.

Только если held-out тест покажет пользу, усложнять до observer с состоянием [s,v,a_drive,d] и полной ковариацией или небольшого ансамбля режимов. Большая нейросеть, RL и end-to-end предсказание xyz без геометрии здесь не являются первым шагом.
